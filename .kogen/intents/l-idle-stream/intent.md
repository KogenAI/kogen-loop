# End provider attempts that make no progress

Slug: l-idle-stream
Model: .kogen/intents/l-idle-stream/model.qnt invariants=Bounded,IdleOnlyWhenSilent seed=7 samples=200 steps=30
Acceptance:
- .kogen/intents/l-idle-stream/acceptance.feature
- features/steps/l_idle_stream.js

Fix L-IDLE-STREAM (change_type: fix): a provider attempt whose response makes no progress for the existing silence limits must end as a classified transient provider failure, whatever the connection does, and the existing retry policy then applies. Today (b4a4185) the per-attempt watchdog in `provider/idle.go` (`firstByteChatGPT = 90 * time.Second`, `firstByteDefault = 45 * time.Second`, `streamIdle = 180 * time.Second`, `idleWatch`) already ends an attempt whose connection is open but truly silent: a scratch test against a real local `httptest` server on the current tree saw both non-streaming Chat Completions (`exchangeChat`) and Responses end as `failed` with `end_reason` `idle` 180 s after the last byte, then retry and complete. The gap it does not cover is bytes that are not response progress: `idleWatch.observe(at, n)` renews the idle clock for any positive read, so a stream that sends progress once and then only SSE keep-alive comments (`: keepalive\n\n`) stayed open 400 simulated seconds after its last progress and would stay open until the 30-minute absolute budget. This Intent replaces "any body byte renews the clock" with "only response progress renews it", adds one record field so the run log shows when the last progress came beside when the last byte came, and adds regression tests with a real local fake server and the injectable `Client.Now`.

Rules (they replace the current "any actual body byte, a heartbeat or a partial frame included, renews the idle clock" rule):

- Streaming routes (Responses `/v1/responses` for ChatGPT and SuperGrok, Anthropic Messages): a body read is response progress when it completes at least one SSE event (a block ending in a blank line, LF or CRLF framing) that has at least one `data:` field and is not a keep-alive. Keep-alives are blocks made only of comment lines (lines starting with `:`, for example `: keepalive`, `: ping`, `: heartbeat`) and blank lines, and, on Messages, `ping` events (`event: ping` or a data object whose `type` is `ping`). An unfinished event counts in the read that completes it (its terminating blank line), not earlier. Every other data event counts, including Responses `response.created`/`response.in_progress`, error events and Messages events the parser otherwise ignores.
- On streaming routes the first-byte limit (90 s ChatGPT, 45 s SuperGrok and Anthropic) is met only by the first progress read; response headers and keep-alives do not meet it. After the first progress, the 180 s idle clock restarts only at a progress read.
- Whole bodies (the non-streaming Chat Completions body of OpenCode Go and openai-compatible, and every HTTP error body read whole on any route): the headers stay the first byte and start the idle clock, unchanged; a body read renews the clock only when it contains at least one byte other than JSON whitespace (space 0x20, tab 0x09, LF 0x0A, CR 0x0D).
- Unchanged: the limit values; the boundary (progress strictly before the limit is valid, at the limit the attempt has expired); zero-byte reads are never progress; elapsed time comes from `Client.Now`; a blocked header wait or body read is cancelled by the watchdog when the limit passes; the transient result and its details `no first byte within 90 s`, `no first byte within 45 s`, `stream idle for 180 s`; `end_reason` `idle`, outcome `failed`, error `provider_failure`; the existing retry policy (3 transport attempts, 2 s then 8 s backoff, `Request.Single` single-shot on ChatGPT); the 30-minute absolute budget and caller cancellation taking precedence over an overlapping timeout; request bytes.
- Run log: every provider attempt record (the `record` of the `request.attempt` event the CLI writes to its JSONL stdout, and of every `provider.Observer`) gains `last_progress_ms`: integer milliseconds relative to the attempt's start of the latest progress read (streams) or of the headers or latest non-whitespace body read (whole bodies), or null when none came. `last_byte_ms` keeps its meaning (the latest positive read of any bytes, keep-alives included), as do `headers_ms`, `first_byte_ms`, `ttft_ms`, `max_gap_ms`, `gap_hist` and `stream_bytes` (still counting every byte). An attempt ended by silence therefore shows `end_reason` `idle` with `last_byte_ms` and `last_progress_ms`; a null `last_progress_ms` on a streaming route means no first progress came.

Boundaries: no new option, limit, timeout or retry change; standard library only; no paid requests; nothing in Kogen, its vendored copy or its pin changes. Update `docs/contract/loop-v1.md` (the silence-timeout bullet under "Client response budget" and the stream-observations bullet, which lists `last_progress_ms` and says Chat Completions and error-body reads set `headers_ms`, `last_byte_ms` and `last_progress_ms`) and add one CHANGELOG v0.1.0 (unreleased) entry for L-IDLE-STREAM.

Tests use local fake servers (`net/http/httptest`) or the existing scripted `obsTransport`, and the injectable `Client.Now`/`Client.Sleep` (`clock` in `provider/helpers_test.go`). No sleep is used as synchronisation: the test waits on channels signalled by the server handler and by a read-signalling `http.RoundTripper` wrapper installed as `Client.HTTP`, advances the simulated clock only after the client has read what was sent, and uses a bounded real-time guard only to fail instead of hanging. Provider tests may lower the unexported `idlePoll` as `TestStreamIdleBlocked` does; the conformance test uses the default poll. The builder owns the named Go tests the acceptance runs; they are not protected artifacts.

## Decisions
- An attempt whose response makes no progress for the existing idle limit ends as a classified provider failure whatever the connection does (silent, or sending only keep-alive bytes), and the existing retry policy then applies; the limit values do not change. (source: request)
- The run log shows when the last byte arrived and why the attempt ended: the `request.attempt` record keeps `last_byte_ms` and `end_reason` `idle` and adds `last_progress_ms`. (source: request)
- The regression reproduces a stream that stops sending while the connection stays open, and one that sends only keep-alive bytes, on streaming routes and on the non-streaming Chat Completions path, with a local fake server and the injectable clock; no sleeps as synchronisation, no paid requests. (source: request)
- No new option, limit, timeout or retry change; standard library only. (source: request)

## Tests
- A response that stops sending while the connection stays open ends the attempt at the existing limit and is retried: TestIdleStreamSilentServer in ./provider. It uses a real `httptest` server for ChatGPT Responses, Anthropic Messages and OpenCode Go Chat Completions. Cases: headers then nothing on streams, which ends at 90 s (ChatGPT) or 45 s (Anthropic) after dispatch; progress then nothing, which ends 180 s after the last progress, including a Chat Completions body that stops after its first 10 bytes. It asserts the first record has outcome `failed`, `end_reason` `idle`, error `provider_failure`, and `last_byte_ms` and `last_progress_ms` equal to the time of the last progress (null `last_progress_ms` when none came). It asserts the server's request context ends (connection closed), one 2 s backoff, and a completed second attempt. Three stalled attempts give an error containing `did not answer after 3 attempts` and the matching detail. (regression)
- Keep-alive bytes neither meet the first-byte limit nor renew the idle clock: TestIdleStreamKeepAlive in ./provider, with a real `httptest` server sending keep-alives on the test's command every 100 simulated seconds. Responses sends `: keepalive\n\n`. Messages sends `: ping\n\n` and `event: ping\ndata: {"type":"ping"}\n\n`. Chat Completions sends `\n` and space bytes, before the JSON value and after its first 10 bytes. After one progress read, the attempt ends idle 180 s after that progress although a keep-alive arrived 80 s earlier: the record has `end_reason` `idle`, `last_byte_ms` later than `last_progress_ms`, and the detail `stream idle for 180 s`. Keep-alives only from dispatch on a stream end at the first-byte limit with null `last_progress_ms` and the detail `no first byte within 90 s` or `no first byte within 45 s`. The retry completes. This test fails on the unfixed tree. (regression)
- Progress at the boundaries and healthy long streams: TestIdleStreamProgress in ./provider, with the scripted `obsTransport`. A progress event completing 1 ms before 180 s renews the clock (completes); one at exactly 180 s is too late (idle). A partial event split across reads renews only in the read that carries its blank line. An 800-simulated-second Responses and Messages stream with progress gaps under 180 s and keep-alives between completes with `end_reason` `complete` and one request. A Chat Completions body whose non-whitespace bytes arrive within 180 s completes, and the healthy Chat Completions record has `last_progress_ms` equal to its last body read. (regression)
- The run log shows the stalled attempt's last byte and why it ended: TestIdleStreamRunLog in ./conformance. It drives `loop.Session` with a `provider.Client` (injected `Now`, `Sleep` and read-signalling `HTTP`) against a local ChatGPT fake. The first response sends progress then only `: keepalive\n\n` with the connection open; the second answers a message. The emitted events contain `request.attempt` n=1 with outcome `failed`, `end_reason` `idle`, `last_byte_ms` later than `last_progress_ms`, then a completed `request.attempt`, then `round.ended`. (integration)
- Superseded heartbeat and partial-frame renewal: update TestStreamIdleGap (its `heartbeats` and `partial frames` cases now expect idle when only keep-alives or an unfinished event fill the gap), TestStreamIdleLongStream (gaps filled by progress, not heartbeats) and TestStreamIdleAbsoluteBudget (`streamingFor` sends progress events so the budget, not idle, ends it). Keep TestStreamIdleFirstByte, TestStreamIdleCompatibility, TestStreamIdleBlocked and the budget/wait tests passing, adding `last_progress_ms` where they compare record fields. (existing)
- Contract, changelog and project checks: inspect `docs/contract/loop-v1.md` and CHANGELOG.md; run go-format, go-test, go-vet and go-build. (existing)

## Feasibility
- Scratch observation by this shaping session (a /tmp copy of b4a4185 plus one throwaway test, not a Kogen probe record): a real `httptest` server that sent a progress prefix and then held the connection open ended the attempt at 180 simulated seconds as `failed`/`idle` with a completed retry, on both OpenCode Go Chat Completions and ChatGPT Responses (go test exit 0, 0.02 s). Plain silence is already covered.
- Scratch observation: the same Responses server sending `: keepalive\n\n` every 100 simulated seconds after one progress event left the attempt open 400 s after that progress (go test exit 0, 2.0 s; the attempt was ended only by cancelling the context). This reproduces the keep-alive gap the Intent fixes.
- Scratch observation: a read-signalling `http.RoundTripper` wrapper set as `Client.HTTP`, together with `clock.advance`, synchronised the real-server tests without sleeps.
- Model typechecked and run with Kogen Quint: `quint run --backend=typescript --invariant='Bounded and IdleOnlyWhenSilent' --seed=7 --max-samples=200 --max-steps=30` found no violation. A variant whose keep-alive resets the clock violates the invariants, so the model distinguishes the fix from the old behavior.
- The draft acceptance ran on the unfixed scratch copy: all four scenarios fail because the named tests are absent, and each message names the test, its `go test -json` command and the outcomes.
- Documentation lookups (Anthropic streaming docs, OpenRouter keep-alive docs) were denied in this session and returned no body. The keep-alive forms come from repository evidence: SSE comments in the fixtures `provider/stream_idle_test.go` (`idleBeat`), `provider/wait_test.go` and `provider/response_budget_test.go`; Messages `ping` events, which `provider/messages.go` already ignores as "pings and unknown informational events"; and RFC 8259 JSON whitespace for whole bodies.
