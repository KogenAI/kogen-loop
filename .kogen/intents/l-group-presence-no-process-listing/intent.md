# Answer group presence without ps on macOS

Slug: l-group-presence-no-process-listing
Model: not applicable — the change replaces how one stateless membership question is observed on macOS; the callers' waits, signals, keeper and supervisor rules and their transitions are unchanged
Acceptance:
- .kogen/intents/l-group-presence-no-process-listing/acceptance.feature
- features/steps/l-group-presence-no-process-listing__presence.js

Today `groupOthers(pgid, self int) (bool, error)` in `sys/lifeline.go` answers "does process group pgid have a live member other than self". It reads `/proc` when `/proc/self/stat` reads non-empty (`procGroupOthers`). Otherwise, which on macOS is always, it calls `psGroupOthers`, which starts `ps -A -o pid=,pgid=,stat=`, reads the whole process table and parses it. Every question therefore costs a fork, an exec and a scan of every process on the machine. The question is asked every 20 ms by the wait after SIGKILL in `Terminate` (`sys/sys.go`, `groupOthers(g, 0)`), every 200 ms by the keeper (`keeperMain`), every 100 ms by `sweepOwnGroup`, and once by the supervisor when its command ends (`MaybeSupervise`). On this Mac, 20 questions took about 340 to 400 ms. The timeout path (`timeoutGroupAlive` in `sys/timeout_observation_darwin.go`) already answers a similar question with the kernel's process-group query, `sysctl {CTL_KERN 1, KERN_PROC 14, KERN_PROC_PGRP 2, pgid}`, at almost no cost.

After this change, on macOS (darwin) `groupOthers` answers from that same kernel query. It neither reads `/proc` nor starts `ps` or any other process. The rules stay the same: zombies are not members, `self` is excluded (a `self` of 0 excludes nobody, as `Terminate` uses it), and a failed observation is an error, which callers keep treating as presence. On every other system `groupOthers` is unchanged: `procGroupOthers` when `/proc/self/stat` reads non-empty, otherwise `psGroupOthers`. Both functions stay in `sys/lifeline.go`, unchanged and without a build tag. The existing `TestPsGroupOthersIgnoresItsOwnListing` keeps calling `psGroupOthers` on macOS too.

Interfaces (package `sys`, unexported, darwin only, in a new file such as `sys/group_others_darwin.go` with `//go:build darwin`):
- `func groupRecords(pgid int) ([]byte, error)` returns the kernel's `kinfo_proc` records for the group, zombies included. It is the query `timeoutGroupAlive` makes today: a size query, then always a data query into a buffer of `max(size, 1)` bytes. It returns exactly the bytes the successful data query reported, returns any errno as an error, and returns a reported size larger than the buffer as an error ("truncated group query"). `timeoutGroupAlive` may be rewritten as `len(records) != 0` over it; its behavior and the timeout tests stay unchanged.
- `func kernelGroupOthers(pgid, self int, records func(pgid int) ([]byte, error)) (bool, error)` calls `records(pgid)` for the asked group. If that call fails, it returns `(false, err)`, keeping the error for `errors.Is` (returned as is or wrapped with `%w`); a failed query is never reported as absence. Otherwise it walks the records, 648 bytes each (`struct kinfo_proc` on darwin arm64 and amd64): `kp_proc.p_stat` is the byte at offset 36 (`SZOMB` = 5), and `kp_proc.p_pid` is the little-endian int32 at offset 40. It returns `(true, nil)` at the first record whose pid differs from `self` and whose state is not `SZOMB`, and `(false, nil)` when there is none. It never reads past the returned bytes; a length that is not a whole number of records is a failed observation (an error).
- On darwin, `groupOthers(pgid, self)` returns `kernelGroupOthers(pgid, self, groupRecords)`. The per-platform selection is the Build's choice, for example a small per-platform helper that `groupOthers` consults before its `/proc` and ps branches. It must keep the non-darwin behavior above exactly.

Unchanged: `Terminate`, `sweepGroup`, `sweepOwnGroup`, the keeper and supervisor and their intervals, `afterCommand`, `LiveGroups`, `Retire`, `ForeignKill` and `Session.Owned` (whose own ps listing is not a group-presence question), `procGroupOthers`, `psGroupOthers`, the Linux and other-system timeout observation files, every event, tool text, the caller contract (`docs/contract/loop-v1.md`), options and exported signatures. Standard library only; go.mod gains no requirement. The existing `sys/*_test.go` files stay byte-identical. The change touches only files under `sys/` (other than `sys/foreign_kill.go` and `sys/error.go`, which hold the refusal and error texts) and its own Intent files. Every file outside `sys/`, `.kogen/` and `features/` stays byte-identical: the README, the docs and contract, `go.mod`, `api/`, `loop/`, `tools/`, `provider/`, `cmd/`, `contract/`, `conformance/` and `scripts/`, where events, tool texts and contract rows live.

Acceptance runs a Go program kept as text in the step file. The steps write it to a temporary file and run `go run -overlay <file> features/steps/l-group-presence-no-process-listing__driver.go`. The overlay serves the program at that virtual path, and serves at the virtual path `sys/lgpnpl_export_darwin.go` an acceptance-only file that exports `LgpnplGroupOthers` (calling `groupOthers`) and `LgpnplKernelGroupOthers` (calling `kernelGroupOthers`) to it. Neither file exists or may be created; nothing is written into the checkout. The program leads a new process group (`setpgid(0, 0)`) and sets its `PATH` to a directory whose single entry is a `ps` shim that records each start and then execs `/bin/ps`. It then does the following, in order:
1. It asks `groupOthers(own group, own pid)` in 5 rounds of 20 questions. It reports each round's duration, the answers, and whether `getrusage(RUSAGE_CHILDREN)` changed during the rounds.
2. It asks about its own group with `self` set to its own pid, then with `self` set to 0.
3. It calls `kernelGroupOthers` with a `records` function that fails with a sentinel error.
4. It starts `/bin/sleep 600` leading its own group and asks about that group three times: while the sleep is live, after SIGKILL once `/bin/ps -o stat= -p <pid>` reports `Z` (unreaped), and after reaping, when `kill(-pgid, 0)` reports ESRCH.

Finally it prints one JSON object, including how many times the `ps` shim started.

The unchanged-files scenario fingerprints, with sha256 over each path and its content in sorted path order, every file `git ls-files --cached --others --exclude-standard` lists outside `sys/`, `.kogen/` and `features/`, plus `sys/foreign_kill.go` and `sys/error.go`. That was 198 files before this change.

Reserved for acceptance (do not create these, and do not use the names in the product or its tests): the paths `features/steps/l-group-presence-no-process-listing__driver.go`, `sys/lgpnpl_export_darwin.go` and `sys/lgpnpl_control_darwin.go`, the exported names `LgpnplGroupOthers` and `LgpnplKernelGroupOthers`, the `lgpnpl` identifier prefix in package `sys`, and the environment variable `LGPNPL_PS_LOG`.

## Decisions
- On macOS, the group-presence question is answered by the same direct kernel group query that timeout observation uses (sysctl KERN_PROC_PGRP), without spawning any process (source: request)
- Kept rules: zombies are not members, the asking process is excluded, and a failed observation is an error that callers treat as presence (source: request)
- The /proc path and the ps fallback stay for other systems; no change to any event, tool text or contract row (source: request)

## Source comparison
- Addressed, Problem: on macOS, `groupOthers` stops starting `ps -A` for every question. The wait after SIGKILL in `Terminate` (20 ms), the keeper (200 ms), `sweepOwnGroup` (100 ms) and the supervisor's one question all reach the kernel query through `groupOthers`; their intervals are unchanged.
- Addressed, Need: the same direct kernel query as timeout observation (`groupRecords` is that query; `timeoutGroupAlive` may share it unchanged). Zombie exclusion (`p_stat` 5), `self` exclusion and error-as-presence are kept. `/proc` and the ps fallback are kept for other systems.
- Addressed, Need ("No change to any event, tool text or contract row"): scenario 5 requires every file outside `sys/`, `.kogen/` and `features/` (the contract, docs, events and tool texts), plus `sys/foreign_kill.go` and `sys/error.go`, to keep its pre-change fingerprint.
- Addressed, Synthetic acceptance 1 ("one live member present; only unreaped zombies absent; empty group absent"): scenario 1 checks the answers `group_with_one_live_member` true, `group_with_only_an_unreaped_zombie` false and `empty_group` false, all with no error.
- Addressed, Synthetic acceptance 2 ("the asking process is never counted"): scenario 2 checks `own_group_asked_by_itself` false. `own_group_asked_without_exclusion` (`self` 0, as `Terminate` asks) is true, so exclusion follows `self` and not the caller's pid.
- Addressed, Synthetic acceptance 3 ("a failed kernel query is returned as an error, not as absence"): scenario 3 checks that `kernelGroupOthers` returns the injected query error (`errors.Is`), after querying the asked group.
- Addressed, Synthetic acceptance 4 ("20 times on macOS under 5 ms in total (today about 330 ms) and starts no child process"): scenario 4 requires the median of 5 rounds of 20 questions to be under 5 ms, all 100 answers `false <nil>`, no change in `RUSAGE_CHILDREN` during the rounds, and 0 `ps` starts. Observed on this Mac: about 0.45 ms with the known-good control, and about 400 ms per round with today's ps listing (behind the recording shim). The request's "about 330 ms" is its own measurement; 20 bare `ps` listings took 342 ms here.
- Addressed, Synthetic acceptance 5 ("all existing sys tests pass unchanged"): scenario 6 hashes the ten existing `sys/*_test.go` files, which must stay byte-identical, and runs `go test -count=1 ./sys`.
- Decided here, technical: the names and signatures `groupRecords` and `kernelGroupOthers` (the injectable `records` function exists only because the request requires a failed query to be shown as an error, and no real query can be made to fail on demand), the 648-byte record layout, and that macOS skips the `/proc` read.

## Feasibility
- The kernel query `sysctl {1, 14, 2, pgid}` on this Mac (darwin/arm64, Go 1.27.2, about 790 processes) returns 648-byte `kinfo_proc` records. `p_stat` at byte 36 is 2 for a live process and 5 for an unreaped zombie (which the query still lists), and `p_pid` is at byte 40. After reaping, and for an empty group (pgid 999999 or -1), it returns 0 bytes and no error. 20 size+data queries took 0.58 ms; 20 `ps -A -o pid=,pgid=,stat=` listings took 342 ms. (probe 1: exit 0, about 1 s)
- In a scratch copy of the unchanged tree, the acceptance `go run -overlay` driver fails to build with `undefined: kernelGroupOthers` in the overlaid export file (legitimate missing-feature red). With the known-good control it reports every expected answer, `ps_started` 0, no children and rounds of 0.44 to 1.35 ms. With the known-bad control (today's ps listing kept, a kernel function that swallows a failed query) it reports the presence and self answers rightly, but `ps_started` 105, children started, `error_is_the_query_error` false and rounds of 395 to 874 ms. (probe 2: exit 0, about 4 s)
- `/bin/ps -o stat= -p <pid>` reports `Z` for a killed, unreaped child on this Mac, which the acceptance driver uses to wait for the zombie state outside the timed section. (probe 2: exit 0)
