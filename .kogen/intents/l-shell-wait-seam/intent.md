# Run the shell-wait tests on controlled time

L-SHELL-WAIT-SEAM in kogen-loop. On the MacBook (2 Nov, kogen-loop c6e2360, `go test -count=1 -json ./...`) the suite took 130 s of wall time because five tests wait out the real 45-second shell wait: `tools.TestShellYieldRetrievalScope` (77 s), `loop.TestDiscardedAttemptStopsCompletedYieldedShell`, `loop.TestDiscardedAttemptStopsYieldedShell`, `conformance.TestShellLifecycleHandleRetrieval` and `tools.TestShellYieldLargeMalformedOutput` (45 s each). After this change those five tests drive the wait on controlled time through a Go API seam that only tests set, still exercise the real yield, retrieval, discard and large-output paths with real processes, and each still fails on a deliberately broken implementation. Production behaviour and the 45-second wait are unchanged.

**The seam.** `tools.Tools` (tools/tools.go) gets one exported field:

```go
ShellAfter func(wait time.Duration) <-chan time.Time
```

- Nil (the zero value; the CLI, `loop.Session`, `loop.Run` callers and every existing caller): the shell wait uses a real timer exactly as today (`time.NewTimer(wait)`, stopped when the call returns).
- Non-nil: every shell call that reaches the wait (a new command once it has been started, or a retrieval of a known handle) calls `ShellAfter` exactly once with the wait it would otherwise take — exactly `45 * time.Second` for a new command and `30 * time.Second` for a retrieval — whether or not the command has already completed, starts no real timer for that wait, and treats a value received from the returned channel as that wait having elapsed. Calls that end before the wait (argument errors, `error: unknown shell handle`, a context already done) do not call it. Command completion and the context end the wait exactly as today; the results (exit-status text, running/completed JSON envelopes, output bounds, handle registry, cancellation stopping the command) are produced by the same code as with a real timer.
- `ShellAfter` only decides when a wait elapses; it cannot change the 45-second or 30-second durations, which stay fixed in tools/tools.go. Its doc comment states that it is a test seam, that production leaves it nil and that a shell call passes it the wait it would otherwise take.
- It is not a CLI flag, task field, `loop.Round`/`loop.Session`/session-config field, config key, environment variable or anything a user of the CLI can set. The CLI and `loop.Session` never set it.
- Deadline policy: cancellation and the round deadline (`deadline_seconds`, a context deadline) reach the shell wait as the context passed to `RunContext`/`CallContext`; tests drive them on controlled time with a context they cancel or whose `Done` channel they close. No second clock is added.
- Kogen constructs `&tools.Tools{...}` itself (its Build and Review native tools), so it can set the same field in its silent-shell tests (K-SILENT-SHELL-TEST-FAST builds on this item). No Kogen source, vendored copy, pin or installation changes here.

**The five tests** are restated to set `ShellAfter` on the `tools.Tools` they already use (the conformance test sets it on its `newLifecycleRun` round's Tools). Each keeps every assertion it makes today except the wall-clock windows, which are replaced by stronger checks on the controlled wait:
- `tools.TestShellYieldRetrievalScope`: the yield window (44–52 s), the running-retrieval window (29–36 s) and the completion wake window (1–6 s) become: the new command asks `ShellAfter` for exactly 45 s and the retrieval for exactly 30 s; each call stays blocked until the test fires its controlled wait; after the release, the retrieval returns `completed` without its controlled wait having fired. Kept: running envelope with output `one` and a nonempty handle; a padded handle returns `error: unknown shell handle`; the running retrieval returns output `one`; two completed retrievals with `exit_status` 7 and output `onetwo`; after `EndShellRound` the five invalid argument sets return `error:` text and no `bad` file is created.
- `tools.TestShellYieldLargeMalformedOutput`: unchanged assertions (valid JSON envelope of at most 16384 bytes, `running` then `completed`, output starting `�xxx`, ending `xxx�` and containing `bytes omitted`).
- `loop.TestDiscardedAttemptStopsYieldedShell` and `loop.TestDiscardedAttemptStopsCompletedYieldedShell`: unchanged assertions (running yield with handle; discarded handle becomes unknown; the completed yielded leader's child survives between calls and is stopped by the discarded attempt).
- `conformance.TestShellLifecycleHandleRetrieval`: unchanged assertions (3 provider requests; initial running result with output `partial\n`; retrieval completed with output `partial\ncomplete\n` and `exit_status` 7) through `loop.Run`.

A test fires a controlled wait only after the command has observably produced what the following assertion expects (for example a marker file the command writes after its output), so yields stay deterministic under load and `-race`. The tests do not sleep to let real time pass (short polling for files a command writes is fine). Each of the five passes in at most 10 s and, under each deliberately broken implementation of the acceptance, fails by its own assertion in at most 30 s, never by hanging until the `go test` timeout. No assertion is removed or loosened, no timeout or limit is raised, and all cases are synthetic (local processes and scripted providers, no paid calls). Other tests that still wait on the real wait (`tools.TestShellYieldLargeJSON`, `tools.TestShellRetrievalCancellationStopsCommand`, the subtests of `conformance.TestShellLifecycleYieldSnapshot`) are not among the five and stay unchanged.

**Mutation anchors.** The acceptance builds deliberately broken implementations in private copies of the tree by replacing these existing lines, so each must stay verbatim and occur exactly once in its file (comments must not repeat them): in tools/tools.go `45 * time.Second`, `30 * time.Second`, `if len(raw) > maxResult {` and `envelope["exit_status"] = res.Status`; in loop/overlap.go `s.tl.CancelShellHandle(result.Handle)` and `sys.Terminate(owned)`. The change needs none of them edited.

**Documentation.** docs/contract/loop-v1.md "Shell time limit" keeps "The wait is not a setting" and adds one sentence naming `Tools.ShellAfter` as a test seam: when set, a shell call passes it the wait it would otherwise take and treats a value from the returned channel as that wait elapsing; production leaves it nil. No CHANGELOG entry (commit history records changes).

**Report.** The Build reports, on the same host and at the same load, back to back, the wall time of `go test -count=1 -json ./...` on the base commit d481382 (in a separate copy, for example extracted with `git archive`) and on the candidate tree, and the `Elapsed` of each of the five tests in both runs.

## Decisions
- The seam is the exported Go field `tools.Tools.ShellAfter func(wait time.Duration) <-chan time.Time`, nil in production; it is never a CLI flag, config key, environment variable or anything a user can set. (source: request)
- Production behaviour and the 45-second new-command wait are unchanged. (source: request)
- The five named tests drive the wait on controlled time, still exercise the real yield, retrieval, discard and large-output paths, and each still fails on a deliberately broken implementation. (source: request)
- Kogen can use the same seam in its silent-shell tests. (source: request)
- No assertion is weakened, no timeout or limit is raised, cases are synthetic only. (source: request)
- Before/after suite wall time on the same host at the same load is reported. (source: request)

## Tests
- A non-nil `ShellAfter` receives exactly 45 s for a new command and 30 s for a retrieval, holds the call until fired, and completion, cancellation and a deadline end an unfired wait: acceptance harness `TestAcceptShellWaitSeam` (independent, private copy) and restated `tools.TestShellYieldRetrievalScope` (integration)
- The five named tests run on controlled time, keep their assertions and each pass within 10 s: restate `tools.TestShellYieldRetrievalScope`, `tools.TestShellYieldLargeMalformedOutput`, `loop.TestDiscardedAttemptStopsYieldedShell`, `loop.TestDiscardedAttemptStopsCompletedYieldedShell`, `conformance.TestShellLifecycleHandleRetrieval`; acceptance scenario `The five shell-wait tests no longer wait out the real shell wait` (integration)
- Each of the five still fails on a deliberately broken implementation, by its own assertion within 30 s: acceptance mutation outline (regression)
- With `ShellAfter` nil the CLI keeps the real 45-second wait and 30-second retrieval behaviour: acceptance `long` CLI scenario reusing `features/steps/l_bounded_shell_wait.js`; existing l-bounded-shell-wait acceptance and `tools.TestShellNewCommandCompletesWithinBound`, `tools.TestShellNewCommandCancellationStopsCommand` (existing)

## Feasibility
- Repository inspection: the only shell timer is `timer := time.NewTimer(wait)` in `(*Tools).shell` (tools/tools.go:630) with `wait := 45 * time.Second` / `30 * time.Second` (lines 627–629) and a select over completion, the timer and `ctx.Done()`.
