# Record when a read recovers lines a cut omitted

Slug: l-cut-recovery-observability
Model: not applicable — the session only appends one record per cut read_file result and compares each later read_file result with those records; the comparison is a pure function of line numbers, with no transitions or interacting rules worth modelling
Acceptance:
- .kogen/intents/l-cut-recovery-observability/acceptance.feature
- features/steps/l-cut-recovery-observability__session.js

Today a standalone session (`loop.Session`, and so `kogen-loop run`) emits a `tool.result` event whose `cut` is `true` when the engine cut the delivered text to 16384 bytes. The `tool.call` event of every later call carries only `call_id`, `name` and `arguments_sha256`. The run log therefore cannot show whether a later `read_file` brought back the lines a cut left out. After this change, two additive `tool.result` fields make that recovery observable. Neither field records file contents, file paths or raw call arguments. Nothing the model receives changes.

New fields on `tool.result` (emitted from `Session.Round` in `loop/session.go`, beside the existing `cut`, `rule`, `shell_wait`, `error_kind` and `malformed_class`):

- `omitted_lines`: `[a, b]`, a JSON array of two integers. It appears only on the `tool.result` of a `read_file` call whose delivered text was cut (`cut` is `true`) and whose raw result is numbered `read_file` text (every line is `N<tab>…` with consecutive numbers, the same test `numberedRange` in `tools/tools.go` applies). `a` is the number of the line holding the first omitted byte and `b` the number of the line holding the last omitted byte. Each line counts with the `\n` that ends it. For a line-aligned cut this is exactly the range the marker already shows: the marker `[... 334 lines (70-403), 20618 bytes omitted ...]` gives `"omitted_lines":[70,403]`. A byte-only cut inside long lines gives the lines that were delivered only in part, or not at all. No other result carries the field: uncut reads, cut results of other tools (for example `shell`), errors and notices.
- `recovers`: a JSON array of objects `{"call_id": <id>, "lines": <n>}`. It appears only on the `tool.result` of a `read_file` call whose result is numbered `read_file` text and that delivered at least one line of an earlier cut read of the same file. For each such earlier cut there is one entry, in the order the earlier cut `tool.result` events were emitted. `call_id` is the earlier cut call's `call_id` exactly as its `tool.call` and `tool.result` events show it. `n` (at least 1) is how many line numbers in that cut's `omitted_lines` range this result delivered as complete lines. When this result is not cut, its delivered lines are all the lines of its raw text. When it is cut too, they are its raw text's lines minus its own `omitted_lines` range. A result that recovers nothing has no `recovers` key: not an empty array, not `null`.

Rules:

- "Earlier" means a cut `read_file` whose `tool.result` event came before this one in the same `loop.Session`, across all of that Session's rounds. The session keeps these records in memory only. They are not written to `session.json`, and `ResumeSession` starts with none. Because `kogen-loop run` runs one round per process, the CLI ties recoveries within that round. `loop.Run` emits no events and is unchanged.
- "Same file" compares the root-relative cleaned path that read_file's path argument resolves to: the path is joined to `Root` when relative and passed through `filepath.Clean`, as `expand`/`resolve` do. So `big.txt`, `./big.txt` and `<root>/big.txt` are one file. Symlinks are not resolved for this comparison. The path is used only for the in-memory comparison and never appears in any event.
- A read of another file, or one whose delivered lines all fall outside the omitted range, is not a recovery: for example lines 60–69 or 404–410 against an omitted range of 70–403. A partly overlapping read recovers only the overlap: lines 400–405 against 70–403 give `lines: 4`. An uncut result creates no record, so later reads of that file never carry `recovers` for it. A cut read is never a recovery of itself. A later cut read of the same file gets its own `omitted_lines` and becomes one more record. The file's content is not compared: a file changed between the reads is still matched by line numbers.
- Every event keeps its existing fields and meanings. `tool.call` events keep exactly `call_id`, `name` and `arguments_sha256`. `tool.result` keeps `result_sha256`, `bytes` and `cut` as they are now. The other event types do not change, including the token count `usage.output` in `response`, `round.ended` and `context.condensed`. Only tool-output payload text (file contents) and raw call arguments (including the path and line-range arguments) must stay out of the event stream.
- Everything the model receives stays the same: every `read_file` text, the cut and its marker, definitions, request bodies and the transcript. Capabilities, `capabilities_digest`, CLI commands and flags, task fields and `SessionConfig` also stay the same. No option, setting or `api` constant is added.

Update `docs/contract/loop-v1.md`: add `omitted_lines` and `recovers` to the `tool.result` row of the events table, and add a short note under "Tool result cut (fixed)" that states the rules above. The contract's rule for an additive v1 change asks for a contract note and a conformance fixture. Do not touch CHANGELOG.md.

## Decisions
- The run log identifies a later read that covers lines a cut omitted and ties it to the cut call's id. Reads of another file, reads outside the omitted lines and reads after an uncut result are not reported (source: request)
- The event record carries no file contents and no raw call arguments, and the tool results delivered to the caller (the model) do not change (source: request)
- Per the delivery decision after build d746f707, the leak check applies to tool-output payload text and raw arguments only. `usage.output` (a token count) and every other existing event field stay unchanged and are allowed (source: request)
- The recovery is recorded on the recovering read's `tool.result` as `recovers` (cut call id and number of omitted lines it delivered), and the cut read's `tool.result` gains `omitted_lines` so that full or partial recovery can be read from the log alone (source: request)

## Source comparison
- Addressed, Problem: "tool-call events retain only a digest of their arguments" and "cannot establish whether a later file read recovered omitted content". `tool.call` stays digest-only. `tool.result` gains `omitted_lines` on the cut read and `recovers` on the recovering read. Acceptance scenario 1 checks both through the built CLI.
- Addressed, Need: "distinguish a subsequent read that covers omitted content from unrelated reads, without recording file contents or raw tool arguments. Preserve the existing tool behavior and output." The fields hold only call ids and line numbers or counts derived from what was delivered. Both scenarios check that no file text, file path, `start_line`/`end_line` name or raw arguments string appears anywhere on stdout, and that every delivered `read_file` text equals the exact current text.
- Addressed, Synthetic acceptance 1: a scripted session cuts `big.txt` (600 lines, omitted 70–403) and then reads `./big.txt` lines 100–109 and `big.txt` lines 400–405. The events show `recovers` `[{"call_id":"c-cut","lines":10}]` and `[{"call_id":"c-cut","lines":4}]` (scenario "recovery").
- Addressed, Synthetic acceptance 2: reading `other.txt` lines 100–109, `big.txt` lines 60–69 and 404–410 (each next to the omitted range), and reading the uncut `small.txt` twice give no `recovers` (scenario "unrelated").
- Addressed, Synthetic acceptance 3: both scenarios check for leaks and for unchanged output.
- Superseded: the first shaped observer rejected any `"output":` key in the event stream, including the existing `usage.output` token count, and Build d746f707 stopped as build_blocked. This observer compares only the fields that `tool.call` and `tool.result` add beyond their existing ones. It searches all of stdout only for fixture file text, paths and raw argument strings, so `usage.output` is allowed. The good observer control contains `usage.output`.
- Decided here, technical: per-Session in-memory records, lexical path identity, and line-number matching that ignores file changes. The request does not settle these, and they keep the change additive and free of any extra I/O.

## Tests
- A cut read_file result reports `omitted_lines`, and a later read of the same file (spelled `./big.txt` too) that delivers omitted lines reports `recovers` with the cut call's id and the count, partial overlap included: acceptance scenario "recovery" through the built CLI, plus a new conformance test (for example `conformance/cut_recovery_test.go`) that runs a `loop.Session` against the existing fake provider and checks the same fields. That test is the conformance fixture the contract asks for (integration)
- Reads of another file, reads whose lines are all outside the omitted range (adjacent on both sides), and reads after an uncut result carry no `recovers`. Uncut results carry no `omitted_lines`: acceptance scenario "unrelated", plus the same cases in the conformance test (integration)
- Two cut reads of the same file followed by a read inside both omitted ranges give two `recovers` entries in emission order, and a byte-only cut of a read_file result with lines longer than the bound reports the partly delivered lines as `omitted_lines`: the conformance test (integration)
- No file contents, paths or raw arguments reach the event stream, `tool.call` keeps exactly its fields, and every delivered read_file text is unchanged: both acceptance scenarios (scenario)
- Existing tool texts, cut markers, hashes, `cut`, other events and `loop.Run` keep their behavior: the existing `go test ./...` suites keep passing unchanged (existing)

## Feasibility
- Repository inspection: `tool.call` and `tool.result` events come only from `Session.Round` in `loop/session.go`. Its `HandleCall` hook already sees the raw `tools.Output` and its cut form for each call, and its `AfterCall` emits `tool.result`. With hooks set, `loop.Run` runs a batch's calls one after another, so the order of `tool.result` events is deterministic. The cut and the numbered-text test are in `tools/tools.go` (`Cut`, `cutText`, `cutLines`, `numberedRange`). Path resolution is `expand`/`resolve`. No external protocol, provider or library fact is involved, so no documentation lookup was needed.
- Scratch probe against unchanged HEAD e077526 with Go 1.27.2. `tools.Cut` applied to the numbered text of the 600-line fixture `big.txt` (36875 bytes) delivers 16308 bytes with the marker `[... 334 lines (70-403), 20618 bytes omitted ...]`. The feature's expected cut output uses this marker.
- The scripted provider follows the existing CLI acceptance drivers (`features/steps/l_tool_error_classes.js`): a fake ChatGPT credential, `KOGEN_PROVIDER_URL`, and Responses SSE frames. The l-tool-error-classes acceptance showed that the current stdout carries no call arguments or tool output texts.
- Observer controls were run with Node 24.21.0 on a scratch copy of the submitted driver. The good control accepts the expected streams, including `usage.output`. The bad control rejects every mutation: a dropped, shifted or extra `omitted_lines`/`recovers`, a wrong call id or count, a recovery on an unrelated read, a tool-output payload key, an extra `tool.call` field, leaked file text, paths or raw arguments in other events, changed or missing outputs, a no-call ending, an error event and exit 1.
