# Wait up to 45 seconds for new shell commands

Slug: l-bounded-shell-wait
Model: not applicable — only the initial wait of a new shell command changes (1 s to 45 s); shell lifecycle states, handles, retrieval, custody and cleanup stay unchanged
Acceptance:
- .kogen/intents/l-bounded-shell-wait/acceptance.feature
- features/steps/l_bounded_shell_wait.js

Fix L-BOUNDED-SHELL-WAIT in kogen-loop (Studio issue 3943154d-e0e0-4c5f-ad74-0e956b93552d, change_type improvement). Today a new shell command (`shell` called with `command`) waits at most one second and then returns a running handle, so the model spends a whole request only to fetch the result. After this change a new command waits at most 45 seconds. If it finishes within that time, the same tool response carries its exit status and output as today's fast-command text `exit status: <n>\n<combined output>`, with no handle. A command still running at 45 seconds yields the existing running JSON envelope (`status: "running"`, opaque `handle`, cumulative `output`) and keeps running. This replaces the one-second initial wait in `tools/tools.go` (`wait := time.Second` for new commands). Handle retrieval is unchanged: it waits at most 30 seconds, returns as soon as the command completes and returns cumulative output.

The 45-second bound is fixed. It is not a task field, CLI flag, option, environment variable or exported setting, and no test seam is exported for it. Waiting never kills: a command that outlasts the bound stays alive after the yield. Cancellation and the round deadline (`deadline_seconds`) end the wait and stop the command and its group before the call returns, as they do today during the one-second wait. 166ec7f's round cleanup (`EndShellRound`, round custody) and attempt cleanup (discarded-attempt handle cancellation and group retirement) are unchanged. Background children of a command that completes within the bound are stopped by round custody when the round returns, as for sub-second commands today. They stay alive between the round's calls. Foreign-kill refusal, output bounds, JSON envelopes, handle scoping, `error:` texts and `sys.Options.Timeout` are unchanged. No Kogen vendored copy, pin, installation, publication or CHANGELOG change: the Kogen re-pin and its checks are delivery's step after landing.

## Decisions
- A new command waits at most 45 seconds and returns immediately when it completes. Completion within the bound returns `exit status: <n>\n<combined output>` in the same tool response, with no handle and no fetch request. A longer command still yields a handle. (source: request)
- Cancellation and the round deadline end the wait and stop the command. Waiting never kills. 166ec7f's round and attempt cleanup is unchanged. Background children of a completed command are stopped by round custody at return, as for sub-second commands today. (source: request)
- No new command, flag or option. (source: request)
- Tests that encode the old 1 s initial yield are restated and keep their lifecycle assertions. (source: request)
- The model-facing shell description states the new wait. Its sentence "A new command waits up to one second; retrieval waits up to 30 seconds." becomes exactly "A new command waits up to 45 seconds; retrieval waits up to 30 seconds." The rest of the description is unchanged. (source: request)

- Addressed, Acceptance evidence: "a command that finishes in a few seconds returns its exit status and output in the first tool response with no handle and no fetch request" is the `fast` scenario. ## Feasibility
- Repository inspection: the single initial-wait timer is `wait := time.Second` at tools/tools.go:627. Retrieval (30 s), completion wake-up and context cancellation already share that select, so no external protocol, library or provider capability is involved and no documentation lookup was needed.
- Scratch control outside the checkout (git archive of HEAD with only that constant set to 45 s and the description sentence changed): the submitted acceptance passed 4/4 in 56 s, and the first `long` result arrived after 45008 ms. On unchanged HEAD all 4 scenarios failed for the intended reasons: the first result was a running envelope after about 1005 ms, there were 2 requests for cancel and deadline, and the description was the old one.
- The same scratch control ran `go test ./tools ./loop ./conformance -count=1`. It identified the failing old-yield tests listed in Source comparison and the conformance slowdown from 52 s to 404 s caused by serial `TestShellLifecycleYieldSnapshot` subtests.
