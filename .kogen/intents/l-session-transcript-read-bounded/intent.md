# Bound the session transcript read on resume

Slug: l-session-transcript-read-bounded
Model: not applicable — resume makes one size decision on one file before decoding it; there is no stored state, transition or interacting rule beyond the existing load-then-compare sequence, which is unchanged
Acceptance:
- .kogen/intents/l-session-transcript-read-bounded/acceptance.feature
- features/steps/l-session-transcript-read-bounded__resume.js

Today `loop.ResumeSession` (in `loop/session.go`, reached from `kogen-loop run` when the task has `session.resume: true`) calls `os.ReadFile(filepath.Join(cfg.Dir, "session.json"))` with no size limit and then decodes it through `json.NewDecoder(bytes.NewReader(data))`, so a very large transcript, or a file that is not a transcript at all (a wrong directory passed as the session directory), costs memory and time proportional to its size, and a second in-memory copy, before the first check can refuse it. A 67108865-byte sparse file is read whole today (about 64 MiB allocated) and refused only as `the session transcript is not valid: invalid character '\x00' looking for beginning of value`; a valid transcript padded with trailing spaces to 67108864 bytes resumes but also allocates about 64 MiB.

After this change:
- `loop/session.go` has a named, unexported constant `transcriptLimit = 64 << 20` (67108864 bytes). It is far above every transcript a normal run writes: the conversation a round sends is kept under the 524288-byte request ceiling by condensation, and one provider response body is read to at most 64 MiB on any wire. (Technical choice made in shaping; the request asks for a named bound large enough for every transcript a normal run writes.)
- `ResumeSession` keeps its order up to the read: an empty `cfg.Dir` and `build(cfg)` errors come first, unchanged. Then it opens `<cfg.Dir>/session.json` and stats the open file (`f.Stat()`) before reading any byte of it.
  - The file does not exist: unchanged, `loop/session_mismatch` with detail `no session transcript at <path>`.
  - The open or the stat fails otherwise: `loop/session_mismatch` with detail `cannot read the session transcript: <error>` (the existing prefix).
  - Its size is above `transcriptLimit`: refused with `loop/session_mismatch` (exit 2, the existing `mismatch` helper) and the detail `the session transcript at <path> is <size> bytes, more than the limit of 67108864 bytes`, where `<path>` is `filepath.Join(cfg.Dir, "session.json")` exactly as in the missing-file message and `<size>` is the stat size in decimal (for example `the session transcript at /tmp/s/session.json is 67108865 bytes, more than the limit of 67108864 bytes`). Nothing of the file is read and no request is sent; the CLI emits its usual `error` event `{class: loop, reason: session_mismatch, detail: ...}` and `session.ended` `{status: failed, exit: 2}`.
  - Its size is at most `transcriptLimit` (exactly 67108864 bytes included): the transcript is decoded directly from the open file (`json.NewDecoder` over the file, read through `io.LimitReader(f, transcriptLimit)` so a file that grows after the stat is still read at most to the bound), with `UseNumber` as today, and the file is closed before `ResumeSession` returns. No `os.ReadFile`, `io.ReadAll` or other full in-memory copy of the file is made besides the decoder's own buffering, so a short transcript followed by trailing whitespace up to the bound is resumed while `ResumeSession` allocates far less than the file size (fewer than 4194304 heap bytes for a 67108864-byte file). A decode error keeps today's detail `the session transcript is not valid: <json error>` (for the text `not json`: `the session transcript is not valid: invalid character 'o' in literal null (expecting 'u')`; an empty file `...: EOF`).
- Everything after decoding is unchanged: the protocol, conversation, role, instructions-digest and definitions-digest checks with their messages, and the restored session id, input, terminal and `cut_reads`. A transcript at or under the bound resumes byte-for-byte as before: the resumed request carries the saved `input` unchanged, followed by the feedback.
- The write path (`persist`, `writeAtomic` and its temporary-file rename, 0600 file, 0700 directory) is unchanged; `NewSession` reads nothing.
- `docs/contract/loop-v1.md`, "Session resume": state that `resume: true` refuses a `session.json` larger than 67108864 bytes with `loop/session_mismatch` and the message above, before reading it. The `ResumeSession` line of the Go API listing may mention the size bound.

There is no option, flag, task field or event for the bound.

## Decisions
- Resume refuses a transcript larger than a named upper bound with the existing `loop/session_mismatch` class and a message naming the real size and the bound, before reading it (source: request)
- Within the bound the file is decoded directly from the open file without a second full copy (source: request)
- Transcripts at or under the bound resume byte-for-byte as before; a transcript exactly at the bound is accepted (source: request)
- Missing-file, invalid-JSON and mismatch messages are unchanged; the write path and its atomic rename are unchanged (source: request)

## Source comparison
- Request "stats the transcript first and refuses a file larger than a named upper bound ... with the existing `loop/session_mismatch` class and a message naming the real size and the bound, before reading it": addressed by the size rule above, with the bound fixed in shaping at 67108864 bytes (`transcriptLimit = 64 << 20`) and the message naming the path like the missing-file message does; acceptance scenarios "A sparse transcript one byte above the bound is refused through the CLI before any request" and "loop.ResumeSession refuses a sparse transcript above the bound promptly without reading it".
- Request "Within the bound the file is decoded directly from the open file without a second full copy": addressed by the decode rule above; scenario "loop.ResumeSession decodes a transcript exactly at the bound from the open file without loading it whole" resumes a real transcript padded with trailing spaces to 67108864 bytes and requires fewer than 4194304 heap bytes allocated by `loop.ResumeSession` (today about 64 MiB).
- Request synthetic acceptance "A sparse `session.json` above the bound: resume fails promptly with the mismatch class naming size and bound; peak memory stays small": the sparse file is 67108865 bytes; the library scenario requires fewer than 4194304 heap bytes allocated by `loop.ResumeSession` and a return within 1000 ms (today: about 67128000 bytes).
- Request "A normal transcript written by a short session resumes and continues exactly as before": scenario "A transcript written by a short session resumes and continues exactly as before" (same session id, saved input unchanged plus the feedback for call `c1`, `no_call` ending, rewritten `session.json`).
- Request "A missing file and an invalid-JSON file give today's messages": scenarios "A missing transcript keeps today's message" and "An invalid-JSON transcript keeps today's message" with today's exact details.
- Request "A transcript exactly at the bound is accepted": scenario "A transcript exactly at the bound is accepted" through the CLI and the library at-bound scenario (a real transcript padded with trailing spaces to exactly 67108864 bytes).
- Request "mismatch messages are unchanged" and "The write path and its atomic rename are unchanged": kept by the existing conformance tests (`TestResumeRefusesAMismatchBeforeAnyRequest`, `TestTranscriptResumeAfterATerminalEnding`); no new acceptance.
- Omitted: no option or setting for the bound, no change to `persist`/`writeAtomic`, no handling for other non-regular files beyond the existing read error paths.

## Tests
- A transcript larger than the bound is refused with `loop/session_mismatch` naming size and bound, without reading it: a Go test in package `loop` or `conformance` that calls `loop.ResumeSession` on a sparse `session.json` of `transcriptLimit + 1` bytes and asserts the class, reason, exact detail and that no session is returned; plus a subtest of `conformance.TestResumeRefusesAMismatchBeforeAnyRequest` for the CLI (exit 2, no request) (integration)
- A transcript exactly at the bound is accepted and decoded from the open file: a Go test that resumes a real transcript padded with trailing whitespace to exactly `transcriptLimit` bytes and gets a session with the saved session id (integration)
- The CLI refuses an oversized transcript before any request, resumes normal and at-bound transcripts as before, and the library decodes an at-bound transcript without a full in-memory copy: the acceptance scenarios of this Intent through the built `kogen-loop run` and the public `loop.ResumeSession` (scenario)
- Missing-file, invalid-JSON and mismatch messages are unchanged: existing `TestResumeRefusesAMismatchBeforeAnyRequest` and the invalid-transcript check in `conformance/cut_recovery_test.go`, plus this Intent's missing and invalid-JSON scenarios (existing)
- Normal resume and the write path are unchanged: existing `TestTranscriptResumeAfterATerminalEnding` and `TestFailedRoundLeavesTheLastCompletedTranscript` pass unchanged (existing)
