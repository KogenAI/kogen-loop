# Match search_text patterns as RE2 on every host

Slug: search-text-regex-dialect-portable
Model: not applicable — one stateless call: compile a pattern, filter Git's line records; no state or interacting rules
Acceptance:
- .kogen/intents/search-text-regex-dialect-portable/acceptance.feature
- features/steps/search_text_regex_dialect.js
- features/steps/list_files_quoted_paths_driver.go

`search_text` (tools/tools.go `searchText`) today passes the model's pattern to `git grep -E`, whose extended-regex dialect is the host's C library. Escapes models write by habit (`\b`, `\d`, `\s`, `\w`) are not POSIX ERE. Observed on this macOS host (git 2.54.0, Apple Git-157), in a repository whose `a.txt` holds `func main() {}`, `x = 42 tab<TAB>here`, `foo_bar`: `\bfunc\b`, `\s`, `\w+_` and `(o)\1` print `(no matches)`, and `\d+` matches the letter `d` (it found `.gitignore:1:ignored.txt`). On Linux (glibc) `\b` is a word boundary, so the same pattern answers differently per host; tools/tools_test.go even carries a `runtime.GOOS` branch for `\bfunc\b`. After this change the pattern dialect is RE2 as implemented by Go's standard `regexp` package, evaluated inside the tool, so the answer no longer depends on the host's C library, and a pattern RE2 cannot express is an `error:` line, never `(no matches)`.

Behavior (replaces today's `-e <pattern>` route; nothing else in the tool changes):
- Argument checks keep their order and texts: a missing or non-string `pattern` is still `error: argument pattern must be a string` (malformed classes unchanged); then the optional `path` goes through the same root containment and pathspec handling (refusals unchanged, and they still win over a bad pattern: `{"pattern":"(","path":"../x"}` gives today's containment refusal). The pattern is still cut at its first NUL byte (`cString`), as today: `a\u0000b` searches for `a`.
- Then the pattern is compiled with `regexp.Compile` (RE2 syntax, case-sensitive, no flags added). A compile error returns, without running Git, the text `error: invalid pattern: ` followed by the error's text with its leading `error parsing regexp: ` removed, for example `` error: invalid pattern: missing closing ): `(` ``, `` error: invalid pattern: missing closing ]: `[a` ``, `` error: invalid pattern: invalid escape sequence: `\1` `` (backreference `(o)\1`), `` error: invalid pattern: invalid escape sequence: `\Z` `` and `` error: invalid pattern: invalid or unsupported Perl syntax: `(?=` `` (lookahead `main(?=\()`). Its `error_kind` stays `git_failed` (api.ToolErrorGit), the class invalid patterns have today, so hosts see no vocabulary change; no new error kind is added.
- File selection, binary skipping and order stay Git's: still exactly one `Tools.Repo.Run` call, now `grep -z -n -I -E --untracked -e "" -- [pathspec]` (today's argv with the empty pattern in place of the model's pattern; the empty pattern lists every line of every searched text file, as the existing `""` golden case already shows on every host). Each parsed record `<path>NUL<number>NUL<text>LF` is kept only when the compiled pattern matches its `<text>` (the line without its LF, so `^` and `$` anchor at the line's start and end); kept records are rendered exactly as today (`renderPath`, `<path>:<number>:<text>`, joined with `\n`, Git's order, `trimTrailing` of the whole result). A remainder that is not a record is kept as it came, as today. Status 0 with no kept record, and status 1, are `(no matches)`; any other status or a Git that cannot run keeps today's `git_failed` texts.
- Unchanged: tracked and untracked, not ignored files; `-I` binary skipping; path printing and quoting; root containment; the 16384-byte delivery cut; `(no matches)` for a genuinely absent pattern; `list_files`.
- Model-facing description (tools/defs.go `SearchTextTool`): remove ` (git grep syntax)` from the first sentence and insert, after the containment sentence and before `Returns path:line:text matches.`, this exact sentence (each `\b`, `\d`, `\s`, `\w` is one backslash and a letter in the delivered text): `Patterns use RE2 syntax (Go's regexp package) on every host and match within one line: \b, \d, \s, \w, alternation and classes work, and a pattern RE2 cannot express, such as a backreference or lookaround, returns an error instead of no matches.` The full description becomes: `Search the repository's files for a regular expression, optionally under a path inside the repository root; paths outside it, symlinks leaving it and ~ are refused. <that sentence> Returns path:line:text matches. <the unchanged path-printing sentence>`. Regenerate tools/testdata/defs_golden.json.
- Documentation: in docs/contract/loop-v1.md, the Printed paths "Routes" text describes the new `search_text` route (RE2 via Go `regexp`, `-e ""`, records filtered by the pattern, still one `Tools.Repo.Run` call) and the `invalid pattern` error; the `git_failed` row adds "or the `search_text` pattern is not valid RE2". Following the README, no CHANGELOG.md entry.

Consequences for existing tests (update them; they pin the replaced route): tools/testdata/tools_golden.json `{"pattern":"("}` and `{"pattern":"[a"}` now expect the two `error: invalid pattern: ...` texts above, and `{"pattern":"\\bfunc\\b"}` expects `src/main.go:3:func main() {}`; both `runtime.GOOS != "darwin"` branches for `search_text` in tools/tools_test.go `TestToolsMatchTheElixirResults` are removed, so the golden holds identically on every host. The fake `zRepo` in tools/printed_paths_test.go returns fixed records regardless of the pattern, so `TestSearchRecordsKeepTheirText` uses a pattern matching both of its records (for example `x|last`). The fake `olRepo` in loop/tool_overlap_helpers_test.go keys `grep` calls by the `-e` argument, which is now always empty; it must tell search calls apart another way (for example by the pathspec, with `olSearch` passing its key as `path`), keeping what each overlap test asserts. A prototype of this route in a scratch copy made the acceptance pass and showed exactly these failures (the overlap tests hang until the fake is updated) plus the conformance description check that reads defs_golden.json.

## Decisions
- One documented pattern dialect for every host, covering word boundary, digit, space and word-character escapes; a pattern the dialect cannot express is a clear `error:` line, never silently "matches nothing" (source: request)
- The tool description states the dialect in one sentence (source: request)
- Output format, ordering, path quoting, the 16 KiB cut and `(no matches)` for a genuinely absent pattern are unchanged (source: request)

## Source comparison
- Request "Problem" (tools/tools.go:626 `git grep -E`, description "regular expression (git grep syntax)"): addressed; the route and the description text are replaced as specified above.
- Need "one documented pattern dialect that behaves identically on every supported host ... or a clear error": addressed by RE2 through Go's `regexp`, evaluated in-process; acceptance scenarios "A pattern the dialect cannot express is an error" and the `\b`/`\d`/`\s`/`\w` scenarios.
- Synthetic acceptance fixture (`a.txt` with `func main() {}`, `x = 42 tab<TAB>here`, `foo_bar` in a fresh repository): used verbatim as the feature's Background.
- Item 1 (`\bfunc\b` → `a.txt:1:func main() {}`): scenario "A word boundary matches whole words only", plus `\bain\b` → `(no matches)` to tell a boundary from a dropped escape.
- Item 2 (`\d+` → `a.txt:2:...`, `\s` → lines with a space or tab, `\w+_` → `a.txt:3:foo_bar`): scenario "Digit, space and word-character escapes match"; `tab\shere` shows the tab itself matches `\s`.
- Item 3 (`foo|func` → lines 1 and 3): scenario "Alternation keeps working, also with the escapes".
- Item 4 (a pattern the dialect cannot express → `error:` line naming the problem): `(o)\1`, `\Z` and `main(?=\()` with exact texts.
- Item 5 (`zzz-absent` → `(no matches)`; `(` → an error): scenario "An absent pattern still has no matches and an unbalanced parenthesis is an error"; the error text becomes Go's (`` missing closing ): `(` ``) instead of Git's C-library text.
- Item 6 (identical results on macOS and Linux): every expectation in the acceptance and in the updated golden is host-independent, with the per-host branches removed; the Linux run of these same tests is the supported-platform check of the testing rules (section 5.3), not something a single acceptance run can show.
- Unchanged-behavior sentence (format, ordering, quoting, 16 KiB cut): kept; scenario "The searched files stay Git's tracked and untracked text files that are not ignored" pins that ignored and binary files stay unsearched and pathspecs still work under the new route; existing printed-path and cut tests stay.
- Superseded: the `git grep -E` dialect, Git's regex error texts (`error: fatal: -e option, ...`) for search patterns, and the `runtime.GOOS` exceptions in tools/tools_test.go.
