# Cap Chat output and name length cut-offs

Slug: chat-route-output-cap-and-truncation-outcome
Model: not applicable — the change is stateless request rendering and answer classification in one adapter
Acceptance:
- .kogen/intents/chat-route-output-cap-and-truncation-outcome/acceptance.feature
- features/steps/chat-route-output-cap-and-truncation-outcome__steps.js
- features/steps/chat-route-output-cap-and-truncation-outcome__driver/cap_driver_test.go.txt

On the Chat Completions route only (opencode-go and openai-compatible, provider/chat.go), a stage request budget's output ceiling (`RequestBudgetLimits.MaxOutputTokens`) is sent as the output-token limit, and an answer cut at that limit (`finish_reason` `length`) is a distinct, named, retryable outcome instead of `invalid_response`. The Messages route and the Responses route do not change. The Chat refusal of an output limit is replaced by this support; the Responses refusal stays. The provider tests extended are chat_test.go, output_limit_test.go and the budget tests; acceptance runs model-free Go tests in the provider package.

## Decisions
- The Chat body carries a stage budget's MaxOutputTokens as the single field `max_tokens`, set to the ceiling exactly and identical on every retry attempt; with no ceiling (nil budget or MaxOutputTokens 0) no output field is added and the body is unchanged byte for byte. No other output field (for example max_completion_tokens) is sent. (constraint: no new setting, flag or environment variable) (evidence: provider/chat.go; provider/wire.go; provider/budget.go) (assumption: max_tokens is chosen over max_completion_tokens for compatibility with generic openai-compatible bridges; confirm no target host requires max_completion_tokens) (source: request)
- The refusal in provider/wire.go of MaxOutputTokens is narrowed to the Responses wire only; Chat accepts the ceiling and Messages is unchanged. NewRequestBudget keeps rejecting a ceiling above OutputReserveTokens and a negative one; nothing clamps. (constraint: Responses route still fails with provider/unsupported_capability before any request is sent) (evidence: provider/wire.go; provider/budget.go) (source: request)
- A Chat answer with finish_reason `length` is a transient outcome: the attempt result is the existing retryable provider failure kind with detail `<provider label> output cut at the length limit (finish_reason length)`, carries the answer's reported usage (visible in that attempt's usage record) and returns no items, so a partial tool call is never exposed as a valid call. The existing retry policy then applies unchanged (a keyed provider makes up to 3 attempts, then fails with reason `unavailable` naming that detail); no new retry loop is added. (constraint: stop, tool_calls, refusal and every other invalid shape keep invalid_response; the key, headers and endpoint never appear in the error) (constraint: the existing `length` cases in TestOpenCodeGoMalformedAnswersReturnNoExecutableItems, both in its adaptChat loop and in its Respond check, are updated because length is no longer invalid) (evidence: provider/chat.go; provider/respond.go; provider/stream.go; provider/errors.go; provider/chat_test.go) (assumption: exhaustion surfaces as reason unavailable with the named detail rather than a new reason code; confirm this is acceptable as the named outcome) (source: request)
- No profile, key handling, endpoint, log or configuration changes. Any documentation sentence that says the Chat wire refuses MaxOutputTokens is updated to say only Responses does; the budget comment in provider/budget.go is updated likewise. (decision: D4, round 1) (evidence: provider/budget.go; provider/wire.go) (source: request)

- Ceiling above the output reserve is rejected at budget creation: TestChatCapCeilingAboveReserveIsRejected (unit)
- length is the named retryable outcome, partial tool call not accepted, usage kept, no secrets: TestChatCapLengthIsANamedRetryableOutcome (integration)
- Responses still refuses and Messages still carries the ceiling: TestChatCapOtherWiresKeepTheirBehaviour (unit)
- stop and tool_calls finishes unchanged: TestOpenCodeGoWireRecordAndUsage, TestOpenCodeGoRawReplayIsLosslessAndOrdered, TestOpenCodeGoUsageNormalization in chat_test.go (existing)
- Updated malformed-answer test no longer lists length as invalid: TestOpenCodeGoMalformedAnswersReturnNoExecutableItems in chat_test.go (existing)
- The visible-output-limit tests in output_limit_test.go pass unchanged: TestOutputLimitThinkingIsNotVisible (existing)
