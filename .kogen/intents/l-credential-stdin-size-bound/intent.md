# Bound the credential read from non-terminal input

Slug: l-credential-stdin-size-bound
Model: not applicable — one login reads one secret once; there is no stored state or transition beyond the existing save-or-keep of the credential file, which is unchanged
Acceptance:
- .kogen/intents/l-credential-stdin-size-bound/acceptance.feature
- features/steps/l-credential-stdin-size-bound__login.js

Today `Input.secret(ctx)` in `provider/keys.go` reads the secret of every key or token login: `opencode-go`, `anthropic` and `openai-compatible` through `loginKey`, and `claude-code` through `loginToken`, reached from `Client.Login` and `Client.LoginWithBaseURL`. When `Input.Terminal` is false, a goroutine runs `io.ReadAll(in.Reader)` with no limit. A large file or an endless producer on stdin is held in memory, and the login never ends unless the context does. When the context ends, `secret` returns `ctx.Err()` but abandons the goroutine, which keeps reading the input.

After this change:
- `provider/keys.go` has a named, unexported constant `secretInputLimit = 16 << 10` (16384 bytes, more than 100 times a real API key or Claude Code token). From a non-terminal input, the reader goroutine requests at most `secretInputLimit + 1` bytes from `Input.Reader` in total. It ends on the end of input, a read error, or that one byte past the bound (for example `io.LimitReader(in.Reader, secretInputLimit+1)`), and never reads again.
- The bound counts every byte of input, a trailing newline or CRLF included. Input of at most 16384 bytes is handled exactly as today: one terminating line ending is dropped, whitespace is trimmed, and the existing empty, invalid and invalid-UTF-8 ("input interrupted") outcomes apply. A 16384-byte credential with no newline is saved. A 16383-byte credential followed by `\n` is saved. 16385 bytes, including 16384 bytes followed by `\n`, are refused.
- More than 16384 bytes of non-terminal input are refused through the existing invalid-value refusal of the login, even when the bytes read end inside a UTF-8 sequence (never as "input interrupted"). `loginKey` returns `provider/<reason>: invalid <Label> key input; saved login unchanged` (reason `login_failed`, or `login` for Anthropic; exit 4). `loginToken` returns `provider/login_failed: invalid Claude Code token input: the token must be one line of letters, digits, dot, underscore and hyphen only; saved login unchanged` (exit 4). No byte of the input appears in the error's detail, its `Error()` or `Render()`, the session's stdout or stderr, or anything else the login writes. The saved credential file keeps its bytes. An endless input is refused as soon as the 16385th byte is read.
- A cancelled context still makes `secret` return `ctx.Err()` at once, and the login returns it unchanged (`context canceled`). The reader goroutine may stay blocked in a `Read` the input never answers, but whenever the input delivers bytes it consumes at most `secretInputLimit + 1` bytes in total and then returns.
- The terminal path (`Input.Terminal` true: stty silencing and restoring, one `bufio` line read) is unchanged and not bounded. A 32768-byte line typed on a terminal is still saved.

Unchanged: `Input`, `StdinInput`, `Client`, `Login`, `LoginWithBaseURL` and their signatures, every existing message and reason, the save path (`saveKey`, locks, private writes), `validKey`, `validToken`, the CLI, events, and the caller contract (`docs/contract/loop-v1.md`), which does not describe the key reader. Standard library only. The existing tests in `provider/keys_test.go` keep passing unchanged. The new unit tests go there too.

Acceptance runs a Go program kept as text in the step file. The steps write it to a temporary directory and run `go run -overlay <file> features/steps/l-credential-stdin-size-bound__driver.go 16384`. The overlay serves the program at that virtual path, which does not exist and must not be created. Nothing is written into the checkout. The program logs in through the public `provider.NewClient(...)`, `Client.Input` and `Client.Login` with scripted `io.Reader` inputs, each in a fresh temporary HOME that first saves `old-key` through an ordinary login. It reports, per case, the error (class, reason, exit, detail, or the context error), the saved key, the session's stdout and stderr, and whether any of them carries the input marker `XQZJ` that fills every long input. It also reports the bytes consumed from the input and, for completed calls, whether the heap allocated under 64 × 16384 bytes during the login. An endless input supplies 1 MiB of marker bytes, then blocks without ever ending. A login that has not returned within 5 seconds is reported as such. The cancellation case holds the first `Read` until the context is cancelled and `Login` has returned, then lets the input supply freely and waits until nothing has been read for 500 ms.

The step file's `--control good|bad` mode qualifies the observer against readers patched into `provider/keys.go` through the same overlay: a known-good bounded reader, today's unbounded `io.ReadAll`, and a reader cut at exactly 16384 bytes that accepts truncated input. The patches apply to the pre-change text of `provider/keys.go`.

Reserved for acceptance (do not create these, and do not use the names in the product or its tests): the path `features/steps/l-credential-stdin-size-bound__driver.go`, and the `lcssb` identifier prefix in package `provider`.

## Decisions
- The bound applies only to a non-terminal input. The terminal line read stays as today (source: request)
- Input past the bound is refused through the existing invalid key or token refusal, with no part of the input in the message, logs or output, and the saved login unchanged (source: request)
- Reads within the bound, a trailing newline included, give the same value as today (source: request)

## Source comparison
- Addressed, Problem ("`io.ReadAll` with no size limit ... a goroutine that survives a cancelled context"): the non-terminal read in `Input.secret` requests at most `secretInputLimit + 1` bytes and ends there. Scenario 1 shows that an endless input is refused within 5 s after exactly 16385 consumed bytes. Scenario 3 shows that a cancelled reader stops at the bound.
- Addressed, Need ("a small fixed bound, a named constant, many times the longest real credential"): `secretInputLimit = 16 << 10` (16384 bytes) in `provider/keys.go`. Decided here, technical: the value and the name. Real keys and tokens are about 100 to 200 bytes.
- Addressed, Need ("past the bound is reported as an invalid credential through the existing invalid-value path, with no part of the input echoed in the message, logs or events"): scenarios 1 and 2 check the exact existing invalid key and token details for opencode-go, anthropic and claude-code, empty stdout and stderr, `echoes_input` false and the saved `old-key`. The login emits no events of its own. Its error and session output are what a host turns into messages, logs and events.
- Addressed, Need ("reads within the bound, including a trailing newline, and the terminal line-read path behave as today"): scenario 2 checks short credentials with and without `\n` (key and token), a credential of exactly 16384 bytes, 16383 bytes plus `\n`, and a 32768-byte terminal line, all saved as today. Decided here, technical: the trailing newline counts toward the bound, so 16384 bytes plus `\n` are refused (scenario 2).
- Addressed, Need ("after cancellation the reader goroutine does not keep consuming the input beyond the bound"): scenario 3, `consumed_after_cancel_at_most_bound_plus_one` and `reading_stopped`. One byte past the bound is the least a reader must read to tell 16384 bytes from 16385.
- Addressed, Synthetic acceptance 1 ("an endless stdin gives the invalid-credential result promptly; memory stays near the bound"): scenario 1 checks a return within 5 s, `consumed` 16385 and `allocated_under_64_bounds` (under 1 MiB allocated during the login).
- Addressed, Synthetic acceptance 2 ("exactly the bound size is accepted as today; bound+1 is refused"): scenario 2, `bound-*` and `bound-plus-one-*` cases.
- Addressed, Synthetic acceptance 3 ("a normal short credential with and without trailing newline returns the same value as before"): scenario 2, the four `short-*` cases save `SYNTHETIC-short-key`.
- Addressed, Synthetic acceptance 4 ("a cancelled context returns the context error as before"): scenario 3 checks the error `context canceled` (`errors.Is(err, context.Canceled)`) and the saved `old-key`.
- Addressed, Synthetic acceptance 5 ("the refusal message and any event contain none of the input bytes"): every refusal case checks `echoes_input` false over the error's `Error()` and `Render()` and the session's stdout and stderr, and checks the exact detail.

## Tests
- An endless non-terminal input is refused as an invalid key or token after at most 16385 bytes read, with the old key kept: add a regression test in `provider/keys_test.go` that logs in to opencode-go and claude-code with a reader that never ends and counts the bytes it gave (regression)
- Exactly 16384 bytes are saved, 16383 bytes plus a newline are saved, and 16385 bytes (and 16384 bytes plus a newline) are refused with the existing invalid detail and no input in the error or output: add a table test in `provider/keys_test.go` over the key and token logins (unit)
- A cancelled context returns the context error, and the reader then consumes at most 16385 bytes of an input that resumes supplying: add a regression test in `provider/keys_test.go` (regression)
- Short credentials with and without a trailing newline, empty and invalid input, invalid UTF-8 and read errors behave as today: the existing `TestKeyLoginTrimsStoresPrivatelyAndPreservesBytesOnRejectedInput` and `TestKeyLoginInterruptedInputKeepsTheOldKey` (existing)
- The terminal line read is unchanged and unbounded: the existing `TestKeyLoginTerminalEchoIsOffWhileTypingAndRestoredOnEveryPath`, and acceptance scenario 2's 32768-byte terminal line (existing)
- End to end through the public `Client.Login`: acceptance scenarios 1 to 3 (integration)
