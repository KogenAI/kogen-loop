# Stream Chat Completions responses

Slug: chat-completions-streaming
Model: not applicable — the change is a stateless request rendering and a response reader in one adapter
Acceptance:
- .kogen/intents/chat-completions-streaming/acceptance.feature
- features/steps/chat-completions-streaming__steps.js
- features/steps/chat-completions-streaming__driver/stream_driver_test.go.txt

The Chat Completions route (opencode-go and openai-compatible, provider/chat.go, provider/respond.go) sends `"stream": false` and waits for one JSON answer, so a model that takes 53 to 60 seconds to answer fails every attempt at the per-attempt watchdog (provider/idle.go). The route becomes streaming: the request asks for a server-sent event stream, and each chunk that arrives is progress. Scope is provider/chat.go, new files in the provider package for the Chat stream reader, and tests. The Messages and Responses routes, the watchdog constants (firstByteDefault 45 seconds, streamIdle 180 seconds), retry rules and credential handling do not change. The existing stream progress scanner and observer (provider/progress.go, provider/stream.go, provider/streamobs.go) are reused, not duplicated.

## Decisions
- The Chat request body sends `"stream": true` and `"stream_options": {"include_usage": true}` on both opencode-go and openai-compatible; no other field is added, removed or changed, and there is no setting or option for it. (constraint: the body keys stay within the existing set plus stream_options) (evidence: provider/chat.go; provider/baseline_bodies_test.go; provider/chat_test.go) (assumption: compatible hosts that refuse stream_options are not supported; the request says "where the host accepts it" and the repository shows no per-host variability to keep) (source: request)
- A Chat attempt reads the body with the existing sseProgress scanner and streamObs observer (beginStream, read, progress, firstDelta, finish), like exchangeMessages: a completed data chunk is progress for the watchdog, while comment lines, empty keep-alive lines and whitespace are not. (constraint: no change to firstByteDefault, streamIdle or idle.go) (evidence: provider/idle.go; provider/progress.go; provider/respond.go; provider/streamobs.go) (source: request)
- A fixture Chat Completions server that accepts the request, sends no byte for 60 seconds of simulated time, then streams three data chunks (text delta, tool call delta, final chunk with usage) and the done marker gives a successful call with the assembled text, the tool call and the usage, and never an idle timeout. To satisfy this with unchanged limits, the successful 200 response headers of a Chat answer are the first byte of the attempt exactly as the existing Chat route already treats them (observe with progress at the headers), so the 180 seconds idle limit runs from the headers and not the 45 seconds first-byte limit. (constraint: firstByteDefault stays 45 seconds and streamIdle stays 180 seconds; the acceptance asserts both constants) (evidence: provider/idle.go; provider/respond.go; provider/idle_stream_test.go) (source: request)
- Open limit beside the 60 seconds guarantee: a host that sends nothing, not even the response headers, for 45 seconds still ends in the unchanged first-byte timeout, because that watchdog and its constants are not changed. (evidence: provider/idle.go) (source: request)
- A stream that only sends keep-alive comments for 60 seconds, then nothing, has to end in an idle timeout: keep-alive comment lines never renew the idle clock, so the attempt ends `stream idle for 180 seconds` (the existing detail text `stream idle for 180 s`) counted from the headers, even though comments kept arriving until 60 seconds. (constraint: keep-alive comment lines and empty lines are not progress) (evidence: provider/idle.go; provider/progress.go) (source: request)
- A fixture server that sends a first data chunk after 40 seconds, then no byte for 200 seconds, ends in the stream idle timeout (180 seconds). (evidence: provider/idle.go) (source: request)
- The streamed chunks are folded into the same normalized result the JSON path produced: text from delta.content, reasoning from the reasoning fields the host sends, function calls assembled by delta tool_calls index (id and name from the first fragment, arguments concatenated in order), the finish reason, usage (from any chunk, including a final chunk with empty choices) and the response id and model. Exactly one function call results per index, however many fragments carried its arguments. The result goes through the existing validation (finish stop or tool_calls, valid unique calls with JSON-object arguments, finish length transient), so every invalid shape stays invalid_response. (constraint: one tool call per index, never one per fragment) (evidence: provider/chat.go; provider/stream.go) (source: request)
- The stream ends at the `[DONE]` marker without waiting for the server to close the connection; a stream that ends (EOF) before `[DONE]` is accepted only when a finish reason was received, otherwise it is a transient cut like the existing streamed routes.  (evidence: provider/respond.go) (assumption: accepting an EOF after a finish reason is a leniency toward compatible hosts; the request does not state it) (source: request)
- A host that ignores stream and answers a plain JSON body is accepted and normalized exactly as before, whatever its Content-Type: a body whose first non-whitespace byte is `{` is read whole as today, any other body is read as an event stream. HTTP error statuses keep today's classification and body handling. (constraint: no change to retry rules, status classification or credential handling) (evidence: provider/respond.go; provider/idle_stream_test.go) (source: request)
- The kept complete assistant message `opencode_go_message` is rebuilt from the streamed result as one assistant message object (role, content, reasoning fields received, tool_calls with id, type function and function name and joined arguments) and is replayed by chatMessages exactly as before. (evidence: provider/chat.go) (source: request)
- The wire golden for the Chat request body (baseline_bodies_test.go opencode-go and openai-compatible, and the body in TestOpenCodeGoWireRecordAndUsage in chat_test.go) changes only by `"stream": true` and the stream_options field. Other existing provider tests that serve a non-streamed JSON Chat answer keep passing unchanged because a plain JSON body stays accepted. (evidence: provider/baseline_bodies_test.go; provider/chat_test.go) (source: request)
- Send stream true and stream_options include_usage true on both Chat routes; stream reader reuses sseProgress and streamObs; plain JSON body still accepted; keep-alives not progress; watchdog constants unchanged; first data chunk placed at 40 s in acceptance because total 60 s silence conflicts with the 45 s first-byte limit. (decision: D1, round 1) (evidence: provider/chat.go; provider/idle.go; provider/respond.go; provider/progress.go; provider/streamobs.go) (assumption: Not probed: whether real compatible hosts accept stream_options, and whether EOF after finish_reason without [DONE] occurs in practice.) (source: request)

## Source comparison
- Addressed: stream true and stream_options (scenario 6); events normalized into text, calls by index, finish and usage, and a chunk as progress (scenario 1); 60 seconds of silence then three chunks succeeds (scenario 1); keep-alive comments for 60 seconds end in the idle timeout (scenario 2); first chunk at 40 seconds then 200 seconds of silence ends in the 180 seconds idle timeout (scenario 3); plain JSON accepted (scenario 4); four fragments give one call (scenario 5); opencode_go_message rebuilt (scenarios 1 and 5).
- Open limit: the request also says the first byte is a real server-sent event; the acceptance of 60 seconds of silence requires the response headers to count as the first byte, so the first-byte limit applies only to a host that sends not even headers (see Decisions).
- Omitted deliberately: watchdog changes, retry changes, credential changes, other routes, live calls.

## Tests
- Silence of 60 seconds then three chunks succeeds with text, one tool call and usage, limits unchanged: TestChatStreamSlowFirstChunkSucceeds (integration)
- Keep-alive comments for 60 seconds then silence end in the 180 seconds idle timeout: TestChatStreamKeepAlivesAreNotProgress (integration)
- First chunk after 40 seconds then 200 seconds of silence ends in the 180 seconds idle timeout: TestChatStreamSilenceAfterFirstChunkIsIdle (integration)
- A plain JSON body is still normalized: TestChatStreamPlainJSONBodyIsStillAccepted (integration)
- Four argument fragments give one call with joined arguments: TestChatStreamAssemblesFragmentedArguments (integration)
- Request body has stream true and only stream_options added: TestChatStreamRequestBody (integration)
- The Chat wire goldens change only by the stream fields: update baseline_bodies_test.go and chat_test.go (existing)
- Every other provider test keeps passing unchanged: go test ./provider (existing)
- none: the operation handles one response and has no collection of records whose size grows the work against a data store or service
