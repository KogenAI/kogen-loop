# Keep cut-read records across session resume

Slug: l-cut-recovery-survives-resume
Model: not applicable — the records are an append-only list that `persist` copies into `session.json` after a completed round and `ResumeSession` copies back; the recovery comparison against them is the existing pure line-number function, with no new transitions or interacting rules worth modelling
Acceptance:
- .kogen/intents/l-cut-recovery-survives-resume/acceptance.feature
- features/steps/l-cut-recovery-survives-resume__resume.js

Today a standalone `loop.Session` keeps one record per cut `read_file` result in memory only (`Session.cutReads` in `loop/session.go`: call id, file, omitted line range). It uses these records to put `recovers` on a later `read_file` `tool.result` that brings back omitted lines. `ResumeSession` starts with no records, and `kogen-loop run` runs one round per process. So a read in a resumed round that recovers lines an earlier round's cut omitted is never reported.

After this change the records are part of the session state that `persist` writes to `session.json` with the transcript, and `ResumeSession` restores them. `omitted_lines` and `recovers` then behave in a resumed round, in a new process, exactly as they do in one long `Session`. The existing "in memory only, `ResumeSession` starts with none" behavior is replaced.

Saved form (`session.json`, written by `persist` in `loop/session.go`):

- `transcript` gains one member, `cut_reads`, after `input` as the last member. It is omitted when the session holds no records (Go `omitempty`), so a session that never cut a `read_file` result writes byte for byte the same `session.json` as today. Every existing member keeps its name, order and value.
- `cut_reads` is a JSON array of `{"call_id": <id>, "file": <path>, "from": <a>, "to": <b>}` objects, in the order their cut `tool.result` events were emitted, with exactly these four members. `call_id` is the cut call's id exactly as its events show it. `from` and `to` are the two numbers of that result's `omitted_lines`. `file` is the root-relative cleaned path: read_file's path argument, joined to `Root` when relative and passed through `filepath.Clean` (as today), then made relative to `Root` with `filepath.Rel`. When `Rel` fails (a relative `Root` with an absolute path argument), it is the cleaned path itself. For the fixture, a cut read of `big.txt` (or `./big.txt`) under the root saves `{"call_id":"c-cut","file":"big.txt","from":70,"to":403}`. The in-memory record holds the same root-relative value, and "same file" compares it. So `big.txt`, `./big.txt` and `<root>/big.txt` remain one file, and symlinks are still not resolved. The path never appears in any event.
- `persist` writes every record the Session holds when it writes the transcript after a completed round. This includes records of an earlier round in the same process that failed, because those stay in memory today too. A process that dies inside a round leaves the last completed round's `session.json`, records included, as today.

Restore (`ResumeSession`):

- It loads `cut_reads` in saved order as the Session's records. A `call_id` is restored as the same JSON value it was saved as (the existing `UseNumber` decoding), so a restored string id is emitted unchanged in `recovers`. New cut reads of the resumed session append to these records, and the next completed round saves the whole list.
- A `session.json` without `cut_reads` (written before this change, or by a session that never cut a read) resumes with no records and reports no recovery, as today. A `cut_reads` value that does not decode into the record shape fails like any other undecodable transcript, with the existing `loop/session_mismatch` "the session transcript is not valid: …" refusal. No other validation is added.
- `NewSession` still starts with no records.

Unchanged: everything the model receives (request bodies, every `read_file` text, the cut and its marker, definitions) and the conversation saved as `input`; every event type and field (`tool.call` keeps exactly `call_id`, `name`, `arguments_sha256`); the `omitted_lines`/`recovers` rules themselves; capabilities (`session_resume` stays `"transcript"`) and `capabilities_digest`; CLI commands and flags; task fields; `SessionConfig`. No option or `api` constant is added. `loop.Run` is unchanged.

Update `docs/contract/loop-v1.md`. In "Session resume", add `cut_reads` to the `session.json` member list and say what it holds and that it is omitted when empty. In the cut-recovery note under "Tool result cut (fixed)", replace "the records are in memory only, not in `session.json`, and `ResumeSession` starts with none (`kogen-loop run` runs one round per process)" with this behavior: the records are saved in `session.json` as `cut_reads` and restored by `ResumeSession`, and a `session.json` without them resumes with none. Update the `cutReads`/`cutRead` comments in `loop/session.go` that say "memory only". Do not touch CHANGELOG.md.

## Decisions
- The cut-read records are saved with the transcript and restored by `ResumeSession`, so a read in a resumed round (new process) that recovers lines an earlier round's cut omitted carries `recovers` with that earlier call's id and the recovered line count, as in one long session (source: request)
- A record holds only a root-relative cleaned path (never written to any event), a call id and two line numbers (source: request)
- Nothing the model receives, no existing event field, no CLI flag and no option changes; a session directory written before this change resumes with no records, as today (source: request)
- The contract note that says resume starts with none is updated (source: request)

## Source comparison
- Addressed, Need "part of the session state that is saved with the transcript and restored by `ResumeSession`": a new trailing `session.json` member `cut_reads`, written by `persist` and read by `ResumeSession`. Scenario "resumed" checks the saved records after every round, in order: `[[c-cut],[c-cut,c-cut-2],[c-cut,c-cut-2]]`.
- Addressed, Synthetic acceptance 1: 600-line `big.txt`, cut with omitted lines 70-403. Round 1 reads it and ends, and the session resumes in a new process. Round 2's read of lines 400-405 carries `recovers: [{"call_id":"c-cut","lines":4}]` (scenario "resumed", call `c-straddle`). The same scenario also checks `./big.txt` 100-109 (`lines: 10`), a second cut `c-cut-2` saved as one more record, and a round 3 read 400-405 recovering both in emission order. This shows that records created after a resume are saved too.
- Addressed, Synthetic acceptance 2: resumed reads of `other.txt` 100-109 and of `big.txt` 60-69 and 404-410 (adjacent to 70-403) carry no `recovers` (scenario "unrelated").
- Addressed, Synthetic acceptance 3: round 1's `session.json` is rewritten without `cut_reads` (old format) before the resume. The resumed round works (exit 0, `resumed: true`) and its 400-405 read reports no recovery. A round with no records writes no `cut_reads` (scenario "old format").
- Addressed, Synthetic acceptance 4: every scenario searches every round's stdout for file text, file names, line-range argument names and raw argument strings, and checks that `tool.call` adds nothing beyond `call_id`, `name`, `arguments_sha256`.
- Addressed, Synthetic acceptance 5: scenarios "resumed" and "unrelated" rerun the same rounds with `cut_reads` removed before each resume, which is today's behavior. They require every request body to be byte-identical (after replacing the run-specific session id, root and session directory), and each round's `session.json` with its trailing `cut_reads` member removed to be byte-identical too. Every delivered `read_file` text is also compared with its exact expected text.
- Addressed, "Update the contract note that now says resume starts with none": the `docs/contract/loop-v1.md` edits above.
- Decided here, technical: the member name `cut_reads`, its record shape, its position as the last member, omission when empty, and the `filepath.Rel` root-relative form with its fallback. The request leaves these open. They keep an old-format `session.json` byte-identical when there are no records and make the saved path independent of the root's absolute location.

## Tests
- A cut read saved in round 1 is restored on resume, so a round-2 read in a new process that delivers omitted lines carries `recovers` with the round-1 call id and count (400-405 gives `lines: 4`); records added after a resume are saved and recovered in emission order: acceptance scenario "resumed" through the built CLI, plus a new conformance test in `conformance/cut_recovery_test.go` that runs a `loop.Session` with `Dir`, then `loop.ResumeSession`, and checks the `recovers` fields and the saved `cut_reads` (integration)
- Resumed reads of another file or of lines outside the restored omitted range carry no `recovers`: acceptance scenario "unrelated", plus the same cases in the conformance test (integration)
- A `session.json` without `cut_reads` resumes with no records and reports no recovery; a session without records writes no `cut_reads`: acceptance scenario "old format", plus the conformance test resuming a transcript with `cut_reads` removed (integration)
- Request bodies and the saved conversation are byte-identical to the same rounds without saved records, `tool.call` keeps exactly its fields, and no file path or text reaches any event stream: scenarios "resumed" and "unrelated" (scenario)
- Existing session resume, mismatch refusal, in-session recovery, `TestSessionForgetsCutsAcrossSessions` (a new Session starts with none), wire goldens and other events keep their behavior: the existing `go test ./...` suites keep passing unchanged (existing)

## Feasibility
- Repository inspection: `session.json` is the `transcript` struct that `Session.persist` writes with `json.Encoder` (HTML escaping off, struct member order) after each completed round. `ResumeSession` decodes it with `UseNumber` and restores `id`, `input` and `pending`. The records are `Session.cutReads`, appended in `Round`'s `AfterCall` and compared there. The CLI (`cmd/kogen-loop/main.go`) makes `root` absolute and calls `loop.ResumeSession` when `session.resume` is true. No external protocol, provider or library fact is involved, so no documentation lookup was needed.
- Scratch run of the submitted driver against the unchanged CLI (HEAD c0138d2, Go 1.27.2, Node 24.21.0). Every round of each scripted session ran as its own process and resumed. The end, delivered-output, leak and with/without-records comparison checks passed, so request bodies are deterministic after normalizing the session id, root and session directory. The saved-records check failed as missing-feature red (`session.json` has no `cut_reads`), and so did the round-2 `recovers` check in "resumed".
- Observer controls on the same driver bytes: the good control accepts synthetic observations built from the expectations, including the existing `usage.output` count. The bad control rejects every mutation with an assertion error: dropped, changed, reordered or self-tied `recovers`; a spurious recovery; shifted `omitted_lines`; an extra `tool.call` field; leaked file text, paths or raw arguments; a round not resumed or of another session; a no-call ending, an error event or exit 1; a changed delivered output; missing, extra, reordered or absolute-path saved records; `cut_reads` not last or empty; an extra `session.json` member; and differing request bodies or saved conversation in the run without records.
